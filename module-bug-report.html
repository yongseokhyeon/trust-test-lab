STEP 1 · 개념 학습

1. 버그 리포트란?

버그 리포트는 테스트 중 발견한 결함을 개발자가 재현하고, 이해하고, 수정할 수 있도록 정리한 문서입니다. QA 엔지니어의 실력은 버그를 몇 개 찾았는지뿐 아니라, 리포트가 얼마나 명확한지로도 평가됩니다.

💼 실무에서는 Jira 같은 이슈 관리 도구에 버그를 등록하면 개발자, 기획자, PM이 함께 봅니다. 재현이 안 되는 리포트는 "재현 불가(Cannot Reproduce)"로 닫히고, 그 버그는 그대로 사용자에게 전달됩니다.

3. 심각도와 우선순위

둘은 비슷해 보이지만 다릅니다. 심각도는 결함이 시스템에 미치는 기술적 영향이고, 우선순위는 얼마나 빨리 고쳐야 하는지에 대한 비즈니스 판단입니다.

심각도기준예시
치명적시스템 중단, 데이터 손실, 보안 사고, 핵심 기능 전체 불가결제 버튼을 누르면 앱이 종료됨
높음주요 기능이 잘못 동작하고 우회 방법이 없음정상 사용자가 회원가입을 할 수 없음
보통기능 일부에 문제가 있지만 우회 방법이 있음검색 필터 하나가 동작하지 않음
낮음사용에 지장 없는 사소한 문제버튼 문구 오탈자, 정렬 어긋남
⚠️ 심각도 ≠ 우선순위 메인 화면 회사 로고 오탈자는 심각도는 낮음이지만, 모든 사용자가 보므로 우선순위는 높음일 수 있어요.

4. 좋은 버그 리포트의 5원칙

  1. 재현 가능하게: 다른 사람이 따라 하면 똑같이 버그가 나와야 합니다.
  2. 하나의 리포트에 하나의 버그: 여러 문제를 섞으면 추적과 수정 확인이 어려워요.
  3. 사실만, 구체적으로: "이상해요", "가끔 안 돼요" 대신 입력값과 메시지 원문을 적습니다.
  4. 기대 결과의 근거 제시: 요구사항 번호를 함께 적으면 논쟁이 줄어듭니다.
  5. 감정 배제: "개발을 어떻게 한 거냐" 같은 표현은 협업을 망칩니다.
